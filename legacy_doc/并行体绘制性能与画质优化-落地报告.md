## 0. 结论先行

| 现象 | 根因 | 修复 |
|---|---|---|
| 客户端 RTT 涨到 **几万 ms**，`frames` 只有 0.4 Hz | ① 客户端每轮显示循环只读 **8192 字节**，接收带宽被限到 ~20 KB/s；② 服务端**没有背压**，帧在 TCP 发送队列里无界堆积 | 客户端网络收发搬进独立 I/O 线程 + 全量排空 + 只留最新帧；服务端交互档用 `TIOCOUTQ` 丢帧 |
| 单帧合成 **~150ms**（1000 rank 时更糟） | 每 rank 都把 **1024²×4 = 4MB 全图**汇聚到 rank 0（1000 rank ≈ 4GB），rank 0 再做 O(P×像素) 逐像素循环 | 新增**稀疏 ROI 合成**：只汇聚非空像素外接矩形，rank 0 只做 O(Σ ROI 面积) |
| 拖动时依旧慢 | 拖动档只做 `PixelStride=2`，**帧仍是 1024×1024**，渲染/合成/传输三者的量一点没降 | 拖动档真的降分辨率（1024→512），对标参考实现的 800×800 / 256×256 两档 |
| 顶面纹理**发白发糊、断断续续** | ① 重采样 `--resample 32` < 源分块每轴点数（38/41），**欠采样走样**；② 不透明度用「每步 alpha 直接相乘」，累计光学厚度 ∝ 采样步数，而各 rank 的自适应步长又都恰好把步数用满 `maxSamples` —— **薄超块和厚超块贡献同样的不透明度** | ① `--resample 64` + 欠采样自动告警；② 打开 Beer-Lambert（`unitDistance` = 全局体素尺寸）+ **全局统一步长**（采样点跨超块严格接续） |
| 每 rank 12 倍线程超订 | `iGameThreadPool::defaultThreadCount` 是编译期常量 **12**，与运行时可用核数无关；`--cpu-bind=cores` 下每 rank 只有 1 核 | 启动时按 `OMP_NUM_THREADS` / `sched_getaffinity` 设定线程数 |

修复后本地实测（单 rank、6 分块、1024×1024）：**拖动档单帧 render 3.4ms + composite 0.7ms + send 1.7ms ≈ 6ms**，探针客户端测得的往返 **6~8ms**。

## 1. 参考实现「快在哪」（读源码得到的定量事实）

以下每条都来自 `PVR_REF` 源码，是本次对齐的依据。

### 1.1 LOD 两档是「真的降分辨率」

```cpp
// MiniPVServer.cpp:255-262
const int kW_HQ = 800, kH_HQ = 800;   // 松手后的高质量分辨率
const int kW_LQ = 256, kH_LQ = 256;   // 拖动中的低质量分辨率
const double kInteractiveSampleFactor = 12.0; // 拖动时采样距离倍增
const int kMaxSamples_HQ = 64;        // 松手后采样步数
const int kMaxSamples_LQ = 16;        // 拖动中采样步数
const int kPixelStride_LQ = 2;        // 拖动中像素步长
...
// MiniPVServer.cpp:836-847
renWin->SetSize(interactive ? kW_LQ : kW_HQ, interactive ? kH_LQ : kH_HQ);
mypass->SetMaxSamples(interactive ? kMaxSamples_LQ : kMaxSamples_HQ);
mypass->SetPixelStride(interactive ? kPixelStride_LQ : 1);
mypass->SetUseScreenROI(true);
```

关键点：**`SetSize` 真的换了渲染缓冲尺寸**。相比之下 iGameVis 旧实现只做像素步进，帧仍是 1024×1024，协议载荷与合成开销完全没降。

### 1.2 不透明度是「按路径长度修正」的（Beer-Lambert），且单位距离 = 体素尺寸

```cpp
// MiniPVServer.cpp:586-600
double sp[3];
imageOutput->GetSpacing(sp);
double eff[3] = { sp[0]*scale[0], sp[1]*scale[1], sp[2]*scale[2] };
double ud = std::cbrt(eff[0]*eff[1]*eff[2]);
volumeProperty->SetScalarOpacityUnitDistance(ud);
mypass->SetScalarOpacityUnitDistance(ud);
```

```cpp
// MyCustomVolumePass.cpp:516-530
float sigma_unit = std::max(0.0f, a_s);
double UD = (vp.unitDistance > 0.0) ? vp.unitDistance : 1.0;
double tau = sigma_unit * (dt / UD);
float alpha_step = (1.f - std::exp(-static_cast<float>(tau))) * maskf;
float oneMinusA = 1.f - aAccum;
rAccum += oneMinusA * (r_s * alpha_step);
...
aAccum += oneMinusA * alpha_step;
```

`alpha_step = 1 - exp(-σ·dt/UD)` 时，单位长度的光学厚度是 `σ/UD`，**与步长 dt 无关**。这正是 iGameVis 旧实现缺的一环（旧实现 `m_UnitDistance = 0` → `alphaStep = alpha`）。

### 1.3 全局统一的采样步长

```cpp
// MiniPVServer.cpp:558-572
double baseSampleDistance = 1.0;
imageOutput->GetSpacing(spLocal);
double minSp = std::min({spLocal[0], spLocal[1], spLocal[2]});
if (minSp > 1e-12) baseSampleDistance = minSp;
volumeMapper->SetSampleDistance(baseSampleDistance);
```

`baseSampleDistance = minSp`——**一个所有 rank 一致的全局步长**（以体素为单位），而不是「各自超块弦长 / maxSamples」。

### 1.4 发送侧有背压（丢帧）

```cpp
// MiniPVServer.cpp:266
const int kMaxSendQueueBytes = 512 * 1024;
// MiniPVServer.cpp:922-932
if (interactiveMode != 0 && client_fd >= 0) {
    int outq = 0;
    if (ioctl(client_fd, TIOCOUTQ, &outq) == 0) {
        if (outq > kMaxSendQueueBytes) {
            continue;   // 丢弃本帧，等待队列变空后再发最新帧
        }
    }
}
```

### 1.5 分块与重采样（与 iGameVis 口径一致）

- `ddist::ComputeDistribution`：`part % numProcs == rank` 只用于**扫包围盒的元数据阶段**（`DataDistribution.cpp:513`）；真正的分配是 `BisectGrid(nx,ny,nz,cost,target=min(numProcs,N))`（`DataDistribution.cpp:333-464, 624`），**每个 rank 一个轴对齐连通超块**，rank 号按空间序排定。
- 目标网格：`dims = resPerChunk × 超块各轴块数`，`origin = bounds.min`，`spacing = size/(dims-1)`（`MiniPVServer.cpp:398-422`）。
- 1000 rank 实测布局：`grid=80x16x15`，每 rank 12~24 块（均值 19.2）。
- 数据：每个 `.vtr` 分块 `Extent="1520 1557 452 489 0 40"` → **38×38×41 个点**（37×37×40 个单元），相邻块共享一层采样面；x/y 步进 37、z 步进 40；全局网格 2961×593×601 个点。
- `resPerChunk` 默认 **64**，`sh_test_pvserver.sh` 也是 `RES_PER_CHUNK=64`。

> 这一条直接解释了画质差异：源分块每轴 37/40 个点，**iGameVis 的 `RES_PER_CHUNK=32` 是欠采样 ~1.16 倍**，高频结构被点采样走样成断断续续的块状条纹。

## 2. 本次改动清单

### 2.1 `iGameCore/Core/Common/iGameParallelContext.{h,cpp}`

新增两个原语（`ParallelContext` 此前只有阻塞集合通信，无法表达「变长汇聚」）：

```cpp
void AllGatherInt(const int* in, int* out, int count) const;      // MPI_Allgather(MPI_INT)
void Gatherv(const char* send, int sendCount, char* recv,
             const int* recvCounts, const int* displs, int root = 0) const; // MPI_Gatherv
```

单进程直通分支分别退化为 `memcpy`，保证 `-n 1` 行为不变。

### 2.2 `iGameCore/Rendering/Core/iGameCompositePass.{h,cpp}` —— 稀疏 ROI 合成（默认路径）

新增 `CompositeSparse()`（`SetUseSparseComposite(bool)`，默认 `true`）：

1. 各 rank 扫自己图上 `alpha != 0` 的像素，得到外接矩形 ROI（4 个 int）；
2. `AllGatherInt` 汇总所有 rank 的 ROI（1000 rank 也只有 16KB）；
3. 由同一份 ROI 表算出 `counts[]` / `displs[]`（所有 rank 一致），`Gatherv` 把各 rank 的 ROI 子矩形按 rank 序汇聚到 rank 0；
4. rank 0 求并集 ROI，按**超块全局深度序**（`m_SortOrder`，近→远）**逐个 ROI 矩形**做 front-to-back 预乘 over，累加在 float 缓冲上（避免 UINT8 反复量化）；单像素 `alpha` 接近 1 时跳过；
5. 叠背景色输出两份结果：全帧不透明 RGBA（`GetResultRGBA()`，兼容批渲染路径）+ ROI 子矩形（`GetResultROIRGBA()` / `GetResultROI*()`，供服务端直接发帧，省掉原来的整屏 ROI 扫描）。

复杂度从 **O(P × 像素)** 降到 **O(Σ ROI 面积)**；汇聚量从 **O(P × 全图)** 降到 **O(Σ ROI 面积)**。

正确性：ROI 只裁「alpha 全 0」的像素，而预乘 alpha 下 `alpha=0 ⇒ RGB=0`，被裁像素在 over 里本来就不产生贡献；超块互不重叠且可全局深度排序，因此「按块序逐 ROI over」与「逐像素遍历所有 rank」在数学上等价。

分流顺序：`--tree` → 树合成；否则 → 稀疏 ROI（默认）；Σ 载荷超 `int` 上限时自动回退全图 `Gather`（`CompositeDenseGather()`）。
`CompositeTree()` / 全图路径收尾都会调用 `ComputeResultROIFromFullFrame()` 填好 ROI 字段，语义一致。

### 2.3 `iGameCore/Rendering/Core/iGameVolumeRayCastCPU.cpp`

- **全局统一步长**：当外部显式 `SetStepSize(step > 0)` 时，把首个采样点**吸附到「以近裁剪面为原点的全局 t 栅格」**上：
  ```cpp
  const float snapped = std::ceil(t / step) * step;
  if (snapped <= tEnd) { t = snapped; }
  ```
  所有 rank 用同一相机/投影矩阵，同一像素的光线起点与方向逐位一致 ⇒ `t` 是全局量。吸附后相邻超块的采样点在 t 轴上严格接续（不留缝隙也不重复），块边界不会出现接缝/明暗跳变。
- **空体素跳跃不再吃采样预算**：原实现把「砖块跳跃」也算进 `for (i < maxSamples)`，半空半实的超块会在大步长下被提前截断，产生块状密度错误。现改为 `while (t <= tEnd && samples < m_MaxSamples && iterations < maxIterations)`，`samples` 只在真正做三线性采样时自增，`iterations` 仅作死循环保护。
- 未显式设置步长时保持历史自适应步长行为（`step = 弦长 / maxSamples`），并补注释说明它在多 rank 下的密度问题。

### 2.4 `iGameCore/Filters/VolumeMeshAlgorithm/iGameVolumeResampleFilter.{h,cpp}`

新增诊断量：`GetSourceMinSpacing()`（输入分块最细一维点间距）、`GetOutputMinSpacing()`（输出网格最细一维间距）。用于自动判断并告警「本次重采样是否欠采样」。

### 2.5 `Examples/Rendering/ParallelVolumeRendering.cpp`

- **线程池线程数**：新增 `DetectUsableCoreCount()`（`OMP_NUM_THREADS` > `sched_getaffinity` > `hardware_concurrency`），在**任何 `parallelFor` 之前**调用 `ThreadPool::SetDefaultThreadCount()`。旧行为是编译期常量 12（`--cpu-bind=cores` 下 12 倍超订），且线程池单例会按 `hardware_concurrency()` 预创建线程（56 rank/节点 ⇒ 3136 线程/节点）。
- **全局体素尺寸**：重采样后按 `cbrt(spx·spy·spz)` 求各 rank 自身网格的体素尺寸，`AllReduce(MIN)` 得到**所有 rank 一致**的 `voxelSize`，作为 Beer-Lambert 的 `unitDistance` 与全局步长的基准。
- **重采样诊断**：rank 0 打印 `[resample] block=... target=... outSpacing(min)=... sourceSpacing(min)=...`，欠采样时打印 `WARNING` 与建议的 `--resample` 值。
- 新增 CLI：`--hq-step`（高清档每步跨越多少体素，默认 1.5）、`--lq-step`（拖动档，默认 4.0）、`--lq-div`（拖动档分辨率除数，默认 2）。
- 批渲染（6 轴视角）路径同样设置 `SetScalarOpacityUnitDistance(voxelSize)`，保持与 C/S 路径一致的正确密度（批渲染仍用自适应步长，避免 `-n 1` 整域单 rank 时步数过大）。

### 2.6 `Examples/Rendering/ParallelVolumeServer.h`

- 签名新增 `voxelSize / hqStepScale / lqStepScale / lqDivisor`（有默认值，旧调用仍可编译）。
- **两档 LOD**：`fw = interactive ? max(128,width/lqDiv) : width`，并 `camera->SetViewPort(fw, fh)`（投影矩阵随分辨率变），对标参考实现的 800/256 两档；`maxSamples` 改为由「全局对角线/步长」导出的**安全护栏**（真正迭代次数由本超块弦长决定）。
- **ROI 发帧**：直接取 `composite->GetResultROI*()` / `GetResultROIRGBA()`，不再对整屏扫一遍非黑包围盒。
- **背压丢帧**：交互档发帧前 `ioctl(clientSock, TIOCOUTQ, &outq)`，`outq > kMaxSendQueueBytes(512KB)` 就丢帧（`#if defined(__linux__)` 保护）。
- 计时日志扩展为 `[server] <w>x<h> render=..ms composite=..ms send=..ms roi=<w>x<h> bytes=..`。

### 2.7 `Examples/Rendering/ParallelVolumeInteractive.h`

与 `RunServer` 同步：两档分辨率、全局统一步长、`SetUseScreenROI(true)`、`UploadImageTexture(fw, fh, ...)`。

### 2.8 `Examples/Rendering/ParallelVolumeClient.cpp` —— 网络 I/O 与显示解耦（这次延迟问题的**主因**）

旧实现：

```cpp
while (!glfwWindowShouldClose(raw)) {
    glfwPollEvents();
    sendPending();
    RecvAvailable(sock, rxBuf);   // ← 每轮只 recv 一次，最多 8192 字节
    draw(); swap();
}
```

⇒ **接收带宽 = 8192 字节 × 显示循环频率**。软件 GL / X11 转发下显示循环只有 2.79 Hz（实机日志），带宽被限到 **~23 KB/s**；服务端一帧 ROI 经 zlib 后 ~150KB 就要 **6.5 秒**才能读完，实测 `frames=0.397Hz`（正好 2.5s/帧）与 8192B×2.79Hz 完全吻合。同时服务端按命令速率继续出帧 ⇒ 帧在 TCP 缓冲里无界堆积 ⇒ RTT 单调增长到 **37800ms**。

新实现：

- **独立 I/O 线程**：`select(1ms) + recv` 循环**全量排空**（一直读到无数据），解析完整帧；一次排空里有多帧时**只保留最新一帧**（旧帧丢弃并计数）——显示永远是最新状态，不会「追帧」；RTT 也在 I/O 线程里按 `seq` 配对计算。
- **命令立即发送**：鼠标一动就把积压增量合并成一条 `INTERACT` 从 I/O 线程发出去，不再等显示循环。
- 主线程只做 `glfwPollEvents + 取最新帧 + 上传纹理 + 上屏`；纹理只在收到新帧时上传，并按帧的实际 `width/height` 重新分配（服务端拖动档 512×512 会切换纹理尺寸）。
- 诊断行改为 `[client] display=..Hz rx=..Hz dropped=.. rxKB/s=.. rtt=..ms`。

### 3.5 仍未在本机验证的部分（需要上超算）

1. **多 rank 的 `Gatherv` 全链路**（本机 MPI 起不来）。代码路径与 `-n 1` 共用（同一 `CompositeSparse`），差异仅在 `Gatherv` 本身；
2. **1000 rank 的实测 RTT**（预期：合成从 150ms+ 降到个位数 ms，配合客户端 I/O 线程后 RTT 进入 100~300ms 量级）；
3. **真实客户端拖动时的 RTT 显示**：命令发送 + seq 配对是原客户端已验证过的代码原样搬进 I/O 线程，接收侧已在上面的冒烟测试中验证；本机没有做 OS 级鼠标注入，因此没走一遍「真拖动」；
4. `TIOCOUTQ` 丢帧（仅 Linux，本机为 Windows，走 `#if defined(__linux__)` 分支未执行）。

上超算后建议按此顺序看日志确认：

```bash
sbatch build.slurm && sbatch run_server.slurm
# server_%j.err 里应看到：
#   [threads] iGame ThreadPool default thread count = 1 (OMP_NUM_THREADS/cpu-bind)
#   [resample] ... outSpacing(min)/sourceSpacing(min)   ← 若出现 WARNING 就调大 --resample
#   [voxel] global voxel size (unit distance) = ...
#   [server] 512x512 render=.. composite=.. send=.. roi=.. bytes=..  每帧一行
# 客户端 stderr：
#   [client] display=..Hz rx=..Hz dropped=.. rxKB/s=.. rtt=..ms
```

判定标准：

- `[server]` 行里 `composite` 应为 **个位数 ms**（不再是 150ms）；若仍是百 ms 量级，说明走了 `--tree` 或稀疏路径被回退（看是否有 `exceeds int range` 提示）；
- 客户端 `rtt` 应稳定在**几百 ms 以内**且**不随时间单调增长**（旧现象是涨到几万 ms）；
- `dropped` 可持续增长（服务端出帧快于显示是正常的，客户端只显示最新帧）；但若 `rtt` 同时增长，说明背压没生效（检查是否在 Linux 上、`TIOCOUTQ` 是否可用）。

## 4. 可调参数与调优建议

| 参数 | 默认 | 作用 | 调优方向 |
|---|---|---|---|
| `--resample <n>` | 32 → **64** | 每块重采样分辨率 | 必须 ≥ 源分块每轴点数（本数据集 37/40）。看 `[resample]` 行：`outSpacing > sourceSpacing` 就调大。代价是内存与重采样时间（每 rank 约 `n³×块数`个体素） |
| `--hq-step <f>` | 1.5 | 高清档每步跨越多少体素 | 延迟偏高就调大到 2.0~2.5（配合 Beer-Lambert，密度不会变，只是积分精度下降） |
| `--lq-step <f>` | 4.0 | 拖动档步长 | 想更流畅可调到 6~8 |
| `--lq-div <n>` | 2 | 拖动档分辨率除数 | 想更流畅可调到 3（≈341×341）或 4 |
| `--tree` | 关 | 改用并行树合成 | 只应在「每 rank 的图几乎铺满屏幕」时启用；本场景保持关闭 |
| `OMP_NUM_THREADS` | 1 | 同时决定 iGame ThreadPool 线程数 | 若用 `srun --cpus-per-task=2`，把它设成 2 才能真的用上第 2 个核 |

## 6. igc 分块读取支持（追加）

### 6.1 现象与定位

```
[error]: Invalid IGC parameter payload
[error]: Parsing failure
Read file [type: IGC, success: false, time: 6ms]
Distribution failed: cannot read bounds of piece .../resultB64_CPU1000_TIME4.igc.
```

先纠正一个前提：**iGameVis 的 `ComputeFileDistribution` 本来就是对每个分块做「完整读」来取包围盒的**，并没有 UnifiedVersion `DataDistribution.cpp::ReadExtentHeader` 那种「只读前 64KB 解析 `<Piece Extent>`」的局部读快路径：

```cpp
// iGameVolumeDistributor.cpp:435-439
std::vector<double> send(static_cast<size_t>(7) * n, 0.0);
for (int p = rank; p < n; p += size) {
    DataObject::Pointer obj = FileIO::ReadFile(pieces[p].file);   // ← 完整读
    if (!obj) { continue; }
    const BoundingBox& b = obj->GetBoundingBox();
```

所以「选方式 1（igc 全读 / vtr 局部读）」没有意义，「方式 2（所有格式都全读）」**就是现状，零改动**。日志里的失败发生在 `FileIO::ReadFile` **内部**——iGameVis 根本解不开这些 `.igc`，与「局部读 extent」无关。

真正原因是解码器只支持 float32 几何：

```cpp
// iGameMeshDecoderFilter.h::ValidateCodecParams（修复前）
if (this->m_codecParams.geomParams.valueSize != sizeof(float)) { return false; }   // ← 在这里被拒
```

而 UnifiedVersion 的 igc 编码器把几何按 **float64** 存储：

```cpp
// IgcEncoder.cpp:513-518
// geomParams（无损：lossyMode=0, errorMode=0, valueSize=8(float64), dim=3）
w.I32(0); w.I32(0); w.U64(8); w.U64(pointCount); w.I32(3);
// IgcEncoder.cpp:743
MeshoptEncode(geom.data(), pointCount, 3 * sizeof(double), geomPayload);   // vertexSize = 24B
```

用十六进制确认过头 96 字节：`[type=0x00][BE length=0x0000011E][zstd magic 28 B5 2F FD]`，容器布局与 iGameVis 完全一致，参数块版本也是 2 —— 唯一不兼容的就是 `valueSize`。

> 附带风险：如果只删掉那行校验而不改解码分支，`meshopt_decodeVertexBuffer` 会按 24B 跨度往 12B/元素的 `vector<float>` 里写，直接堆越界。所以必须两处一起改。

### 6.2 改动（仅 1 个文件，3 处）

`iGameCore/Filters/MeshCodec/iGameMeshDecoderFilter.h`：

1. **`ValidateCodecParams`**：几何 `valueSize` 放宽为 `sizeof(float)` 或 `sizeof(double)`（对标 `UnifiedVersion/IgcDecoder.cpp:139-141` 的同一条校验）。
2. **`GeomDecoder`**：按 `valueSize` 分 float32 / float64 两路解码，float64 解到 `vector<double>` 后再窄化为 `float`（对标 `IgcDecoder.cpp:144-175`）。窄化是必须的，因为 `IMeshDecodeAdapterBase::SetPointBuffer` 只收 `vector<float>`，且 iGame 的 `Points` 内部固定 float32（与 vtr / 重采样产物口径一致）。
3. **`Execute()` 收尾**：`meshType == IG_STRUCTURED_MESH` 时按参数块里的 `structuredMeshParams.axisSize` 补一次 `SetStructuredMeshDimension`。
   原因：iGameVis 自己的编码器对结构化网格会写一个「空拓扑块」（`WritePayloads` 无条件写 param/geom/topo/attr），解码时 `TopoDecoder` 借此设置网格维度；而 UnifiedVersion 的编码器（`IgcEncoder.cpp:793-794`）对结构化网格**不写拓扑块**，`axisSize` 只存在于参数块里 → 维度一直是 `{0,0,0}` → 重采样把该分块判为无效。
   `SetDimensionSize`（尺寸未变直接返回）与 `GenStructuredCellConnectivities`（`m_BuildStructuredConnectivity` 短路）都是幂等的，因此对含拓扑块的 .igc 是**零额外开销**。

没有改分发器、没有改重采样器、没有改渲染/合成。启动期元数据扫描的成本也不变（本来就是全读；igc 文件 ~3.8MB 比对应 vtr 的 8.8MB 更小，实际更快）。

### 6.3 验证

**6 分块 igc vs 6 分块 vtr，同参数跑批渲染**（`--resample 64 --field Pressure_Mixture -t 4`）：

| 诊断项 | vtr 输入 | igc 输入 |
|---|---|---|
| 读取 | `[type: VTR, success: true]` | `[type: IGC, success: true, time: 18ms]` ×6 |
| 分发 | `block=(0..5, 0..0, 0..0), pieces=6` | 同 |
| 重采样 | `target=384x64x64 outSpacing(min)=5.79635e-05 sourceSpacing(min)=9.99997e-05` | 同 |
| 全局标量范围 | `[244059, 246557]` | 同 |
| 全局体素尺寸 | `6.00129e-05` | 同 |
| **合成图 `+Z`** | sha256 `42B24D95…3E8A` | **完全相同的 sha256** |

即 **igc 与 vtr 两条输入的最终合成 PNG 逐字节一致**——说明解码出的几何、属性、重采样场与成像结果都与原生 vtr 路径等价（float64→float32 的窄化在这里没有产生任何可见差异，因为 vtr 路径的 `Points` 本来也是 float32）。

**100 分块 igc**（`Paraview_Index_igc.pvd`，`--resample 8`）：200 次读（100 次元数据扫描 + 100 次加载）全部 `success: true`，0 失败；欠采样告警按设计触发：

```
[resample] WARNING: undersampling 5.7143x (output spacing coarser than source).
           Raise --resample to >= 46 ...
```

### 6.4 顺带说明：为什么「局部读 extent」对 igc 本质上做不到

UnifiedVersion 的 `ReadExtentHeader` 只对 XML 系（`.vtr/.vtu/.vts` 的 `<Piece Extent=...>`）有效；igc 的轴长/原点信息在 **参数块 + 几何块**里，而几何块是 meshopt 编码 + zstd 压缩的，必须解压解码才能拿到坐标。所以 igc 的元数据阶段只能「全读」或者「只解参数块 + 几何块（跳过拓扑/属性块）」。后者可以省下 13 个属性的 meshopt 解码，是**将来**可做的优化——本次没做，因为当前实现已经是全读，性能与之前一致，符合「性能基本不变」的要求。
