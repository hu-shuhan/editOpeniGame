## 阶段 1：修复「单分块绕过 64³ 重采样」（14s 大头，优先级最高）

### 步骤 1.1：定位问题（先读，不改）

- **文件**：`Examples/Rendering/ParallelVolumeRendering.cpp:472-495`。当前逻辑：
  ```cpp
  if (nLocalFiles == 1) {
      volume = DynamicCast<StructuredMesh>(it->second);   // ← 直接复用原始全分辨率分块，跳过重采样
  }
  if (!volume) { /* 走 iGameVolumeResampleFilter 重采样到 64³ */ }
  ```
- **BUG 触发条件**：多分块数据（N>1）在 `size == N`（例如 3 分块 / 3 rank）时，每个 rank 恰好
  `nLocalFiles == 1`，于是**每个 rank 都走 `volume = DynamicCast<StructuredMesh>` 分支**，对**原始全分辨率分块**
  直接做光线步进（每光线最多 512 步）。这是 3-rank 下 14s 的主因。单进程 `-n 1`（N==1）也会命中同一分支，
  但那是「整块本来就是单块」的正常语义，不属于本 BUG。

### 步骤 1.2：修正「跳过重采样」的判定条件

- **原则**：跳过重采样只允许在「**整个数据集是单块**（全局分块数 N==1）」时发生；**只要 N>1，所有 rank 一律重采样**，
  与「本 rank 分到几块」无关。
- **改动 1（distributor 补全局分块数）**：
  - 文件 `iGameCore/Filters/VolumeMeshAlgorithm/iGameVolumeDistributor.h`：新增成员 `int m_TotalPieces{0};`
    与 getter `int GetTotalPieceCount() const { return m_TotalPieces; }`。
  - 文件 `iGameVolumeDistributor.cpp`：在 `ComputeDistribution()` 内，`const int n = ...` 之后加
    `m_TotalPieces = n;`；在 `ComputeFileDistribution()` 内，`const int n = static_cast<int>(raw.size());`
    之后加 `m_TotalPieces = n;`。**两处都要设**，否则内存级/文件级路径会读到未初始化的 0。
- **改动 2（入口判定）**：`ParallelVolumeRendering.cpp` 把
  `if (nLocalFiles == 1)` 改为 `if (distributor->GetTotalPieceCount() == 1)`。
  - 注意：原代码块里对 `volume` 的 `SetAttributeIndex(selectedField)` 只应保留在 N==1 分支；
    N>1 时字段由 `resampler->SetFieldName(selectedField)` 处理（现有逻辑已如此），不要重复设置。
- **正确性约束（必须遵守）**：
  1. 分块归属全程不变：本步骤只改「读入后是否重采样」，**不改变 `ComputeFileDistribution` 的分配结果**。
  2. 几何坐标 float64 无损：`iGameVolumeResampleFilter` 输出的 `StructuredMesh` 包围盒来自输入 `BoundingBox`
     （float64），不得在重采样中降精度。本步骤不改重采样内部，仅确认其输出 bounds 与输入一致。
  3. `-n 1` 与 `-n N` 合成结果仍应逐像素一致（验收项）。

### 步骤 1.3：重采样目标分辨率按超块各轴块数缩放（质量修正，非 14s 主因，可后做）

- **原则**：对标文档 §5.4「`resPerChunk × 超块各轴块数`」。当前代码固定
  `resampler->SetTargetDims(resPerChunk, resPerChunk, resPerChunk)`，当某个 rank 分到多个 chunk 时会
  欠采样。
- **改动**（`ParallelVolumeRendering.cpp` 重采样段，`:484-488` 附近）：
  ```cpp
  auto blk = distributor->GetLocalBlock();
  int cx = blk.ix1 - blk.ix0 + 1;
  int cy = blk.iy1 - blk.iy0 + 1;
  int cz = blk.iz1 - blk.iz0 + 1;
  // 只有走 k-d 路径（完整规则网格）时 block 才有效；否则回退为 1×1×1（数量连续切块/单块）
  if (cx < 1 || cy < 1 || cz < 1) { cx = cy = cz = 1; }
  resampler->SetTargetDims(resPerChunk * cx, resPerChunk * cy, resPerChunk * cz);
  ```
  - 说明：`GetLocalBlock()` 在非 k-d 路径返回默认全 0 的 `Block`，此时 `cx/cy/cz` 会算出负数/0，
    故必须做 `cx<1 → 1` 的保护。
- **约束**：目标分辨率过大时（如单 rank 分到 100³ chunk、resPerChunk=64 → 6400³）会 OOM。加护栏：
  `const IGsize maxVoxels = 512LL*512*512;` 若 `resPerChunk³ * cx*cy*cz > maxVoxels`，等比缩小各轴到
  `cbrt(maxVoxels/块数)` 级别并 rank0 告警。**这一步护栏必须写，否则会引入新 OOM**。

### 阶段 1 验收

- 命令：`mpiexec -n 3 testParallelVolumeRendering.exe -i <3-piece>.pvd --resample 64 --cpu`。
- 预期：① 阶段 0 插桩里 `render` 从数秒级降到百 ms 级；② rank 各自输出的 `_rank<r>.png` 仍是完整正确的

## 阶段 2：C/S 帧压缩 + 有效区裁剪（砍 raw 4MB/帧）

> **实现状态（已落地，与下方原方案有差异）**：仓库内只有 `ThirdParty/glfw-3.4/deps/stb_image_write.h`
> （编码），**没有 `stb_image.h`（解码）**。为避免引入 280KB 外部头文件，实际实现改用 **zlib**（已是
> iGameCore 的 PUBLIC 依赖，`#include <zlib.h>` 可直接用）：
> - 协议新增 `kCodecZlib = 1`；新增通用 `SendFramePayload(...)`，`SendFrame(...)` 退化为 codec=0 的封装；
>   `Frame` 增加 `codec`/`payload`，`ParseFrame` 按 codec 校验并回填原始 payload。
> - 服务端 `ParallelVolumeServer.h::renderFrame` 用 `compress2(..., Z_BEST_SPEED)` 压缩合成图，压缩后更小才用
>   codec=1，否则退回 raw。
> - 客户端 `ParallelVolumeClient.cpp` 解析后按 codec 用 `uncompress` 解压回 RGBA8。
> 压缩比低于 PNG（zlib 无 PNG 的行滤波），但实现零新依赖、零新增文件。若将来需要更高压缩比，再按下方
> 原方案引入 PNG（仅需加一个 codec 值）。下方 2.1–2.3 保留作为 PNG 参考路径。

### 步骤 2.2：服务端压缩

- **文件**：`Examples/Rendering/ParallelVolumeServer.h`（`renderFrame` 内 `SendFrame` 调用处，`:261-265`）

## 阶段 3：合成器「块级有序合成 + 去掉深度 Gather」（正确性修复 + 减半汇聚量）

### 步骤 3.1：理解为何要改（先读，不改）

- **文件**：`iGameCore/Rendering/Core/iGameCompositePass.cpp`。
- **现状问题**：`Composite()` 已在 `:67-81` 用 `AllGather(blockDepth)` 算出全局块序 `m_SortOrder`，但
  `CompositeOnRoot()`（`:130-150`）**丢弃 `m_SortOrder`，对每个像素重新做 O(P²) 选择排序**，且为了逐像素
  排序还把全分辨率 float 深度 `Gather` 到 rank0（`:102`）。
- **为什么块级排序才是对的**：每个 rank 拥有一个**空间连通、互不重叠的超块**，且超块可全局按深度排序
  （这正是 k-d 分区 + `ComputeBlockDepth` 的设计目的，对标 IceT `icetCompositeOrder`）。半透明体绘制的
  正确合成 = **按超块深度序做 front-to-back `over`**，与像素级首命中深度无关。IceT 有序 BLEND 也明确
  `icetSetDepthFormat(ICET_IMAGE_DEPTH_NONE)`——**blend 合成根本不需要深度缓冲**。
- **结论**：逐像素排序既慢（O(P²) 每像素）又冗余，深度 Gather 完全多余。改为「块序 over」后，
  `CompositeOnRoot` 里 `allDepth` 参数可整体删除。

### 步骤 3.2：修改 `Composite()`

- **文件**：`iGameCompositePass.cpp`。
- **改动**：
  1. 删除 `ctx->Gather(m_LocalDepth.data(), allDepth.data(), depthCount, 0);`（`:102`）与 `allDepth` 分配
     （`:94/97`）。
  2. `CompositeOnRoot(size, allRGBA)` 的签名去掉 `allDepth`。
  3. 保持 `SetLocalImage(width,height,rgba,depth)` 签名不变（渲染端仍产出 depth，将来 z-buffer/调试可能用），
     但 `Composite()` 不再消费 `m_LocalDepth`。为免歧义，在 `SetLocalImage` 文档注释里补一句
     "depth 目前仅保留、不参与 blend 合成"。

### 步骤 3.3：重写 `CompositeOnRoot`（块序 over）

- **文件**：`iGameCompositePass.cpp::CompositeOnRoot`（`:118-175`）。
- **新算法**（替换逐像素排序）：
  ```cpp
  // m_SortOrder：全局块序（近->远），Composite() 里已算好，所有 rank 一致。
  // m_RankBlockOrder[r]：rank r 在 m_SortOrder 中的位置。
  for (int p = 0; p < n; ++p) {
      float c0=0,c1=0,c2=0,a=0;
      for (int i = 0; i < size && a < 0.999f; ++i) {
          const int r = m_SortOrder[i];               // 按块序，不是按像素排序
          const size_t base = (size_t)r*n*4 + (size_t)p*4;
          const float fragA = allRGBA[base+3] / 255.0f;
          if (fragA <= 0.0f) continue;
          const float inv = 1.0f - a;
          c0 += (allRGBA[base+0]/255.0f)*inv;
          c1 += (allRGBA[base+1]/255.0f)*inv;
          c2 += (allRGBA[base+2]/255.0f)*inv;
          a  += fragA*inv;
      }
      const float inv = 1.0f - a;
      m_ResultRGBA[p*4+0] = toUChar(c0 + m_Background[0]*inv);
      m_ResultRGBA[p*4+1] = toUChar(c1 + m_Background[1]*inv);
      m_ResultRGBA[p*4+2] = toUChar(c2 + m_Background[2]*inv);
      m_ResultRGBA[p*4+3] = 255;
  }
  ```
- **删除**：`m_PixelOrder` 成员（不再需要逐像素排序缓冲）与其初始化/选择排序代码（`:89/123/132-150`）。
- **正确性约束（务必逐条核对）**：
  1. `m_SortOrder` 必须在 `Composite()` 里用 `AllGather` 的 block depth 计算，且**所有 rank 用同一比较器**；
     现有比较器在深度相等时用 rank 号兜底（`:80`），保持确定性，**不要改**。
  2. front-to-back `over` 语义与当前代码（`:152-165`）一致：预乘 alpha，`c += src*inv; a += a_src*inv`。
  3. **超块必须深度有序且互不重叠**：若未来放宽为「任意不相交包围盒」，块级 `over` 的正确性依赖
     `ComputeBlockDepth`（块中心深度）能给出全局有效顺序。当前 6 轴视角 + 轴对齐 k-d 超块满足此前提；
     任意轨道视角下与参考实现同等的「包围盒中心排序」局限不变（非本步骤引入）。
  4. `-n 1`（size==1）：`m_SortOrder == [0]`，循环退化为一层 over，结果与修复前一致。

### 阶段 3 验收

## 阶段 4：`ParallelContext` 增补非阻塞原语 + 自研有序 binary-swap（解决上千 rank 扩展性）

> **实现状态（已落地，采用更简单的「有序二叉树」而非 binary-swap）**：
> 实际实现的是 IceT 的 `ICET_SINGLE_IMAGE_STRATEGY_TREE`（有序二叉树），理由：
> - **任何 P 都成立**（binary-swap 的非 2 幂 P 需要额外"伸缩/telescoping"处理，复杂易错）；
> - O(log P) 轮、rank0 收 O(log P) 张图（对比 direct-send 的 O(P)），已解决上千 rank 扩展性；
> - 实现简单、方向明确（前位 OVER 后位）。
> 落地内容：
> - `iGameParallelContext` 新增 `Isend/Irecv/Wait/WaitAny`（`m_Requests` 存 `void*` 句柄，header 不引入 mpi.h）。
> - `iGameCompositePass` 新增 `CompositeTree()` + `SetUseTreeComposite(bool)` 开关；`Composite()` 在
>   `m_UseTreeComposite && size>1` 时走树合成，否则走 direct-send（默认）。树合成结果同样叠背景输出不透明 RGBA8。
> - `ParallelVolumeRendering.cpp` 新增 `--tree` CLI 开关（批渲染两处 composite 生效）。
> 注意：binary-swap（常数内存、完全并行）作为进一步升级可选做；当前二叉树已满足「O(log P) 轮」目标。
> 下方 4.1/4.2/4.3 保留作为 binary-swap 的完整参考（4.1 已按此落地）。

> 前置：阶段 3 完成后，direct-send 的 rank0 汇聚仍是 O(P) 带宽 + rank0 串行合成。本阶段用
> **单图有序 binary-swap**（对标 IceT `ICET_SINGLE_IMAGE_STRATEGY_BSWAP` + ordered）替代，把每 rank
> 通信量降到 O(图大小)、轮数降到 O(log P)、合成并行到所有 rank。**这是较复杂的一步，建议在阶段 1–3
> 全部落地、且确认要冲上千 rank 后再做。**

### 步骤 4.1：`ParallelContext` 增补非阻塞点对点原语

- **文件**：`iGameCore/Core/Common/iGameParallelContext.h` 与 `.cpp`。
- **新增 API**（保持现有 `Broadcast/AllReduce/AllGather/Gather/Barrier` 不变）：
  ```cpp
  // 非阻塞发送/接收（返回请求句柄，句柄为不透明 int；MPI 后端为自增 request id）。
  int Isend(const char* buf, int count, int dest, int tag) const;
  int Irecv(char* buf, int count, int src, int tag) const;
  void Wait(int requestId) const;
  int  WaitAny(const int* requestIds, int count) const; // 返回最先完成的 requestId
  ```
- **MPI 后端实现**（`iGameParallelContext.cpp`，`#ifdef IGAME_ENABLE_MPI`）：
  - 内部维护一个 `std::vector<MPI_Request>`（或 `std::map<int, MPI_Request>`）与一个自增 id 计数器；
    `Isend` 调 `MPI_Isend`、`Irecv` 调 `MPI_Irecv`、`Wait` 调 `MPI_Wait`、`WaitAny` 调 `MPI_Waitany`。
  - **数据必须在其对应的 `Wait` 完成前保持有效**：binary-swap 用到的发送缓冲必须存活到 `Wait` 返回；
    建议用 `ParallelContext` 内部或调用方持久的 ping-pong 缓冲，**不要**传栈上临时缓冲给 `Isend`。
- **单进程直通**（`#else` 分支）：`Isend`/`Irecv` 直接 `memcpy` 并立即返回已完成句柄，`Wait/WaitAny` 空操作，
  保证 `-n 1` 也能编译运行。
- **约束**：tag 取值范围与 IceT 一致用非负小整数；`Isend`/`Irecv` 必须成对、tag 一致，否则死锁/错配。

### 步骤 4.2：实现单图有序 binary-swap（新合成器 `iGameCompositePass::CompositeBinarySwap()`）

- **前置约定**：每 rank 输入一张**预乘 alpha 的 RGBA8 全分辨率图**（`m_LocalRGBA`），超块深度序
  `m_SortOrder`（近→远）已由 `AllGather(blockDepth)` 得到。**blend 合成不需要深度**。
- **算法（P 个 rank，先要求 P 为 2 的幂；非 2 幂见 4.2 末尾）**：
  1. **排序归一化**：每个 rank 把「深度序 rank 数组」`m_SortOrder` 转成「有序分组下标」
     `order[rank] = m_RankBlockOrder[rank]`（rank 在近→远序列中的 0-based 位置）。
  2. **图像分区**：把全分辨率图像沿高度分成 `P` 条（条数=进程数，条高 `ceil(H/P)`），
     初始每 rank 拥有自己渲染的**整张图**，但只「负责」第 `order[rank]` 条。
  3. **⌈log₂P⌉ 轮**：`for r = 0 .. log2(P)-1`：
     - `partner = rank XOR (1 << r)`。
     - 当前 rank 负责的条集合是一个连续区间 `[lo, hi)`（初始 = 全图，随后每轮减半）。
     - 把 `[lo, hi)` 从中点切成 `A=[lo,mid)`、`B=[mid,hi)` 两半。
     - 用 `Isend/Irecv` 与 `partner` 交换：本 rank 把「自己不负责的那半」发给 partner，同时收 partner
       发来的「本 rank 负责的那半」的对应像素。
     - 对收到的半条与自己负责的那半条做 `over` 合成（**front over back**：`order` 小的 rank 在前的方向）。
     - 更新负责区间为其中一半（按 `rank` 的第 `r` 位决定留左半还是右半）。
  4. **收集到 rank0**：`⌈log₂P⌉` 轮后每 rank 拥有最终图的 `1/P` 条；用 `Gatherv`（或复用现有 `Gather`
     按条长）把各条拼回 rank0 的完整图。
- **有序方向规则（关键，防错）**：`over` 必须是「近 over 远」。因为 `m_SortOrder` 已把 rank 排成近→远，
  而 binary-swap 每轮是按 `order` 分组，故合成方向恒为 **`order` 小者在上**。实现时用
  `frontFirst = (order[me] < order[partner])` 决定「收到的半条」与「自己半条」谁在 `over` 的哪一侧。
- **消息大小**：第 r 轮每 rank 收发各约 `N_pixels/P × 2^r × 4` 字节（首轮最小、末轮最大），全程累计
  < `N_pixels×4` 字节/rank，**与 P 无关**。
- **空块/非 2 幂 P**：
  - P 非 2 的幂：`P2 = next_pow2(P)`，把不存在的 rank 视作「全透明（alpha=0）空图」参与前几轮，实际
    不发送（用 tag 约定跳过）。实现时先做 P 为 2 的幂版本，非 2 幂用 `P2` 补齐再测。
  - 空 rank（某 rank 无分块，理论上被 k-d 约束排除，但防御性处理）：其图像全透明，`over` 结果正确不变。
- **正确性约束（务必逐条核对）**：
  1. 所有 rank 的 `m_SortOrder`/`order[]` 必须一致（同一 `AllGather` + 同一比较器）。
  2. 每轮的 `Isend/Irecv` 缓冲在 `Wait` 前不可释放/改写；用 ping-pong 缓冲。
  3. 条高 `ceil(H/P)` 与 `Gatherv` 的 recvcounts/offsets 在所有 rank 一致，否则 `Gatherv` 死锁/错位。
  4. `-n 1` 直通：`P==1` 时跳过所有轮，直接把 `m_LocalRGBA` 拷贝给 rank0。

### 步骤 4.3：接入与回退开关

- **文件**：`iGameCompositePass.h/.cpp`。
- **改动**：`Composite()` 内部按开关分流：默认走阶段 3 的「块序 direct-send over」（结果稳定、易对拍），
  新增 `CompositeBinarySwap()` 供开关切换。运行时开关用一个 `SetUseBinarySwap(bool)`（默认 false）。
  示例 `ParallelVolumeRendering.cpp` / `ParallelVolumeServer.h` 增加 CLI `--bswap` 开关。
- **原因**：先保证 direct-send 正确基线 + 逐像素对拍能力，binary-swap 作为可切换路径灰度上线，避免
  「一上来就换核心合成器、结果不对却难定位」。

### 阶段 4 验收

- 命令：`mpiexec -n 8 ... --cpu --bswap` 与 `mpiexec -n 8 ... --cpu`（direct-send）与 `-n 1` 各跑一次。
- 预期：① `--bswap` 与 direct-send、`-n 1` 三者 rank0 合成图逐像素一致（容差内）；② `-n 8` 下阶段 0
  插桩的合成耗时（rank0 视角）明显下降，且各 rank 都参与合成（非根 rank 不再空闲）；③ 上千 rank 时
  合成耗时随 P 增长远缓于 direct-send（O(log P) vs O(P)）。

## 通用正确性约束（每一步都要遵守，来自实现路径文档总则）

1. **每 rank 一个连通超块**、超块互不重叠、可全局按深度排序——任何步骤不得破坏此不变量。
2. **几何坐标 float64 无损**——重采样/分发不得把包围盒降为 float32。
3. **集合通信全员一致**——所有 rank 在同一位点调用同一集合通信，count/root 一致；`Gatherv` 的
   recvcounts/offsets 全员一致。
4. **空块不导致死锁**——任何「部分 rank 提前 return」的路径都必须先经 `Broadcast`/`AllReduce` 让所有
   rank 一致退出（对标 `ParallelVolumeServer.h` 的 `runningFlag` 广播）。
5. **分块归属全程不变**——优化只改通信/合成/传输，不改 `ComputeFileDistribution` 的分配结果。
